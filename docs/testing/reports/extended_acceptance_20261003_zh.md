### 08:07 UTC 公网 UDP 重新验证

原始报告：`target/extended-acceptance/20261003T080716Z/report.json`。使用同一测试二进制与 Mihomo 1.19.24，重新下载当前真实订阅；23 个节点的 TCP 测速仍为 20 成功、3 未成功。本轮增加同一 SOCKS 接口的 DIRECT 控制组，并将远程 UDP 探测扩大到全部 23 节点。

| 路径 | 目标与范围 | 结果 |
|---|---|---|
| SOCKS UDP → DIRECT | 公共 DNS 1.1.1.1:53 | 收到匹配查询 ID 的有效 DNS 回答；SOCKS UDP 协商与报文控制通过 |
| SOCKS UDP → 订阅节点，默认封装 | 23 节点，各 STUN UDP/3478、DNS UDP/53 | 46 次尝试全部超时，0 个节点取得有效响应 |
| TUN UDP → 订阅节点，默认封装 | 同上 | 46 次尝试全部超时，0 个节点取得有效响应 |
| SOCKS UDP → 订阅节点，packetaddr | 同上 | 46 次尝试全部超时，0 个节点取得有效响应 |

每次等待响应上限为 2 秒；成功必须匹配 STUN 事务 ID 或 DNS 查询 ID，远程路径还必须匹配所选节点的 UDP 连接链。控制组报告沿用了探测函数的 `remote_node_in_chain` 字段名，但该组匹配的是 **DIRECT**，不代表经过远程订阅节点。控制组的 STUN 请求也超时，因此不能把 STUN 单独作为本轮已知可达的公网目标；有效控制来自公共 DNS。

配置与核心 API 的只读统计均显示 23 节点 UDP 标志为 true，但这些标志不是转发成功证据。此次全部节点的短时探测与此前抽样节点较长超时的失败结果一致，仍不能断言任意 UDP 目标永久不可达，或直接判定供应商/核心存在缺陷。下一步需要具有已知可用 UDP 的远程节点或受控远端 UDP 回显服务，结合服务端记录区分远端策略与协议兼容性。

本轮准备与 DIRECT 控制通过，三条远程 UDP 路径失败，整体退出码 1；所有客机恢复步骤、宿主路由/策略规则/DNS/Mihomo 状态及被测业务文件一致性检查通过。没有把失败改成跳过或成功。
